# MiSTer board-device migration checkpoint

Milestone 4 is **complete for its scoped board-model port and directed acceptance tests**. The new devices are connected to `ngage_board`, whose IRQ/FIQ outputs reach the ARM; the MiSTer CPU still remains held in reset. The standalone ARM/board test runs a small program that configures a timer IRQ and FIQ, acknowledges both, and receives a data abort on an invalid boot-register read. Its bus error response replicates the registered top-level response, but it is not a complete `emu` firmware simulation.

## Implemented and tested

- `ngage_icu.v`: three modeled IRQ/FIQ banks, enable set/clear, selected source priority and pending/current reads, plus commit-gated clear events. Unit-0x60 is FIQ bit 3. DMA IRQ source 7 and SIM FIQ source 26 have tested board inputs; the actual devices are not connected yet and the MiSTer top ties both inputs low. The global enable is a latch, as in the simulation, not a proven hardware gate.
- `ngage_timers.v`: staged boot one-shot, periodic timer hypothesis, unit-1 interrupt and unit-0x60 128-cycle FIQ hypothesis. Direct C++/RTL fixtures now compare boot, periodic, unit-1 and unit-60 interrupt edges and simultaneous acknowledgements; these are not verified UPP silicon timings. The periodic rearm clears timer-0 enable as the staged model does.
- `ngage_nos_io.v`: selected NOS counter, compare, enable/status and software interrupt registers. The current staged model uses **two different rates**: 3174 clocks for the calibration counter at 0x0c150112, and 104000 clocks for the NOS counter at 0x0c150116 and its compare. The old plan's single-counter wording must not override this measured software-model distinction. Both rates remain hypotheses about hardware.
- `ngage_cbus_uem.v`: selected configuration, command, payload and completion phases; staged midscale ADC values, power/RTC status, frozen RTC inputs, alarm and UEM IRQ assumptions. Standalone cases for RTC status and ADC agree with both C++ boards. The alarm and 1 Hz timers now follow the staged model’s global 65536-cycle and 104000000-cycle phases. Focused C++/RTL comparisons cover the complete alarm and 1 Hz phases and alarm/acknowledgement ordering; other simultaneous-event cases remain unverified.
- `ngage_mdi_stub.v`: staged diagnostic MDI announcement, observed ring-pointer consumption and NOS event bits. Both C++ references pass the corresponding directed timing fixture; this does not model a DSP or invent an ADSP success response. The MDI status event is presented on the same tick as the ring update. Directed simultaneous pointer-write and W1C cases match both software boards; broader tick parity remains unproven.
- `ngage_gpio_loopback.v`: staged GPIO A/B set/clear and UEM-routed loopbacks, including the self-clearing 0x0c15021c strobe. Standalone and combined-board routing tests pass; other keypad and serial behavior remains incomplete.
- `sim/ngage_board_sim.v`: Verilog-2001 transaction adapter with mutually exclusive HDL claim and external fallback, plus an ownership/error unit test. Separately, the current CPU simulator now has an optional HDL shadow build (`python3 scratch/current-boot/build.py --hdl-board`), exercising the CPU and both device models; `tests/phone/board_shadow/run.sh` checks CBUS, GPIO loopback, version bit, ICU and epbus latches, NOS/diagnostic bank isolation and stalled RAM-backed reads. Shadow mode deliberately updates C++ and uses its IRQ/FIQ. `hdl-exclusive` routes peripheral requests and IRQ/FIQ exclusively to RTL and rejects missing peripheral windows; C++ still supplies and reports external flash/RAM. ARM ownership, IRQ/FIQ, unsupported-device, and trace-export tests pass. Bounded startup comparisons reached 20 million cycles in both modes, before the first modeled timer interrupt. The HDL trace export is simulation-only.
- `ngage_icu_extra.v`: staged ICU configuration, DMA-configuration and epbus word latches. The observed 0x0c120074=3 write and subsequent 0x0c14d000..10 probe latches are modeled, the CBUS 0x8d prerequisite is enforced and the selected feature-on C++ profile agrees in a directed fixture. Starting LCD DMA raises an explicit unmodeled error until an engine is implemented; configuration read/write is not proof of a DMA transfer.
- `ngage_boot_regs.v`: observed 0x080000xx and 0x0c120014/018/034/038 latches and 0x0c004748–0x0c0047fb executable scratch, including errors on reads of unwritten bytes. `ngage_trace_sink.v` produces events for the staged write-only trace ranges; events are not yet buffered or exported to HPS.
- Formerly aliased upload, NOS and GPIO RAM windows have independent storage; directed tests cover retained upload RAM over phone reset and clearing on cold reset. A cold-start scrub initializes those banks before `board_init_done` can release the CPU. The sparse 0x0d register store tracks full addresses and reports an error at its 64-entry limit instead of aliasing them. Four selected retained traces show six distinct generic 0x0d words combined; this is not an exhaustive bound. This is a bounded implementation, not full equivalence to the unbounded C++ map. Board and unmapped errors now use a registered CPU error response rather than being acknowledged as successes.

LCD bus transport command sequencing, readbacks, invalid requests and stalled/uncommitted writes agree with both C++ boards in `tests/phone/lcd_transport/run.sh`; this does not implement pixels or DMA. Directed tests cover ICU masks/priority/clear, timer expiry/rearm, independent NOS counter rates and wrap, CBUS sequencing and errors, scratch validity, address separation, sparse overflow, trace events, and board IRQ/FIQ paths. The selected CBUS cases are checked separately against current and staged C++ models; they are not yet a complete tick-by-tick transaction replay. `tests/phone/board_cpu/run.sh` runs the ARM program; the other focused scripts are under `tests/phone/{icu,timers,nos_io,cbus,boot_regs,sparse_regs,trace_sink,board_irq}/` and use `jotego/simulator:arm64`.

## Later milestones and limits

- Milestone 5 integrates the diagnostic SIM controller and its FIQ source. Milestone 6 supplies the LCD DMA engine and IRQ, framebuffer/video, held/released controls and bounded hardware diagnostics. No device response is fabricated for the tied-off sources.
- Milestone 7 must compare the hardware-bound firmware path, exercise actual HPS transport and persistent media, and verify FPGA resource use, timing and on-board behavior. The current exclusive simulation uses C++ only for external flash/RAM; the separate `tests/phone/mister_board_cpu/run.sh` test exercises the actual HDL CPU, board and flash controller against delayed test-memory responders with no C++ device fallback.
- The 132 retained-trace device/address inventory establishes decoder ownership only. The 64-entry sparse store can fill and faults on overflow. Tests compare selected staged-model transactions and events, not every possible device operation or physical Nokia timing.
- Preserve every billion-cycle CPU/host checkpoint pair, original firmware, C images and requested screenshots. Do not restore old CPU snapshots into a changed Verilated design. Do not launch a long boot or synthesize before the corresponding project gates.

The split RAMs, sparse associative store, reset initialization and CPU/cache remain unmeasured for FPGA resource use and timing. The PLL metadata mismatch, Main DDR reservation, physical HPS save behavior and power-loss limitations documented in the SDRAM and flash/save notes still apply.
