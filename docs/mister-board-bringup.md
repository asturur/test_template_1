# MiSTer board-device migration checkpoint

Milestone 4 is **in progress**, not complete. The new devices are connected to `ngage_board`, whose IRQ/FIQ outputs reach the ARM; the MiSTer CPU still remains held in reset. The standalone ARM/board test runs a small program that configures a timer IRQ and FIQ, acknowledges both, and receives a data abort on an invalid boot-register read. Its bus error response replicates the registered top-level response, but it is not a complete `emu` firmware simulation.

## Implemented and tested

- `ngage_icu.v`: three modeled IRQ/FIQ banks, enable set/clear, selected source priority and pending/current reads, plus commit-gated clear events. Unit-0x60 is FIQ bit 3. Inputs for DMA, SIM and other devices are not yet connected. The global enable is a latch, as in the simulation, not a proven hardware gate.
- `ngage_timers.v`: staged boot one-shot, periodic timer hypothesis, unit-1 interrupt and unit-0x60 128-cycle FIQ hypothesis. These are not verified UPP silicon timings. The periodic rearm clears timer-0 enable as the staged model does.
- `ngage_nos_io.v`: selected NOS counter, compare, enable/status and software interrupt registers. The current staged model uses **two different rates**: 3174 clocks for the calibration counter at 0x0c150112, and 104000 clocks for the NOS counter at 0x0c150116 and its compare. The old plan's single-counter wording must not override this measured software-model distinction. Both rates remain hypotheses about hardware.
- `ngage_cbus_uem.v`: selected configuration, command, payload and completion phases; staged midscale ADC values, power/RTC status, frozen RTC inputs, alarm and UEM IRQ assumptions. Standalone cases for RTC status and ADC agree with both C++ boards. The alarm and 1 Hz timers now follow the staged model’s global 65536-cycle and 104000000-cycle phases. Full cycle-by-cycle parity and simultaneous-event ordering remain unverified.
- `ngage_mdi_stub.v`: staged diagnostic MDI announcement, observed ring-pointer consumption and NOS event bits. Both C++ references pass the corresponding directed timing fixture; this does not model a DSP or invent an ADSP success response. MDI event delivery through RTL has a registered pulse and needs edge-by-edge parity checks.
- `ngage_gpio_loopback.v`: staged GPIO A/B set/clear and UEM-routed loopbacks, including the self-clearing 0x0c15021c strobe. Standalone and combined-board routing tests pass; other keypad and serial behavior remains incomplete.
- `sim/ngage_board_sim.v`: Verilog-2001 transaction adapter with mutually exclusive HDL claim and external fallback, plus an ownership/error unit test. Separately, the current CPU simulator now has an optional HDL shadow build (`python3 scratch/current-boot/build.py --hdl-board`), exercising the CPU and both device models; `tests/phone/board_shadow/run.sh` checks CBUS, GPIO loopback, version bit and stalled RAM-backed reads. C++ remains the IRQ/FIQ source and shadow state is deliberately updated, so this does not prove exclusive ownership or a fallback-free firmware run.
- `ngage_boot_regs.v`: observed 0x080000xx latches and 0x0c004748–0x0c0047fb executable scratch, including errors on reads of unwritten bytes. `ngage_trace_sink.v` produces events for the staged write-only trace ranges; events are not yet buffered or exported to HPS.
- Formerly aliased upload, NOS and GPIO RAM windows have independent storage. A cold-start scrub initializes those banks before `board_init_done` can release the CPU. The sparse 0x0d register store tracks full addresses and reports an error at its 64-entry limit instead of aliasing them. This is a bounded implementation, not full equivalence to the unbounded C++ map. Board and unmapped errors now use a registered CPU error response rather than being acknowledged as successes.

Directed tests cover ICU masks/priority/clear, timer expiry/rearm, independent NOS counter rates and wrap, CBUS sequencing and errors, scratch validity, address separation, sparse overflow, trace events, and board IRQ/FIQ paths. The selected CBUS cases are checked separately against current and staged C++ models; they are not yet a complete tick-by-tick transaction replay. `tests/phone/board_cpu/run.sh` runs the ARM program; the other focused scripts are under `tests/phone/{icu,timers,nos_io,cbus,boot_regs,sparse_regs,trace_sink,board_irq}/` and use `jotego/simulator:arm64`.

## Remaining work

1. Finish the C++ device inventory and compare event/transaction fixtures in detail, especially simultaneous events, write-side ordering, ICU edge timing and the CBUS RTC phase assumptions. The current RTL does not yet prove cycle parity.
2. Check MDI/IRQ event edges and shared RAM behavior against C++ under concurrent access. Do not invent an ADSP self-test response. Add DMA source 7 and SIM FIQ bit 26 only with their actual device modules.
3. Finish unported ICU configuration and DMA registers, epbus clock/power, remaining GPIO quirks, keypad/serial behavior, UEM inputs, and any other reached stateful register blocks. Broad zero-reset latches are not evidence of equivalent device behavior.
4. Implement a true exclusive-owner mode in the C++ harness (the optional shadow build intentionally updates both models), including interrupt ownership, connect trace events to a bounded diagnostic export, and verify the existing generic 0x0c004xxx and diagnostic 0x0d behavior against the C++ model. The sparse store can fill; its explicit error is a limitation, not a complete peripheral model.
5. Run focused tests with realistic bus stalls and then short firmware tests in a new HDL checkpoint lineage. Do not restore old CPU snapshots into a changed Verilated design. Preserve all existing firmware, images, screens and billion-cycle checkpoint pairs. Do not launch a long boot or synthesize yet.

The split RAMs, sparse associative store, reset initialization and CPU/cache remain unmeasured for FPGA resource use and timing. The PLL metadata mismatch, Main DDR reservation, physical HPS save behavior and power-loss limitations documented in the SDRAM and flash/save notes still apply.
