# Where does v5 spend the extra time per SPMark04 frame?

Andrea reports 5.79 fps on v5 and 6.62 fps on ngage2. At equal 78 MHz those rates correspond to 13.47 M and 11.78 M system clocks per frame, a difference of 1.69 M clocks, or 21.65 ms. Treat that budget as provisional until the installed builds and elapsed-time reference are identified. We want attribution in clocks per frame, an implementation with checked outputs, and a second measurement of the original symptom.

## Establish the comparison

1. Use v5 `8546db1` as the reproducible source baseline (two-way 16/16 KiB L1, 32-byte lines, D-side section-TLB XOR, 32 KiB internal-flash backing cache, 39 MHz MMC, 78 MHz CPU). Pin the ngage2 78 MHz RTL and QIP-selected CPU hash. `6e80660` and `ff6dcff` are reference donor builds; identify the board RBF and effective configuration where records allow. Keep ngage2 read-only and preserve existing v5 experiments. Record firmware and helper hashes, original SPMark version, install drive, run mode, display settings and warm/cold state. An unverified RBF can still be compared as an observed run.
2. Collect Game, FillRate and PolyCount from matched runs. Use a fixed count of completed application frames in steady state. Mark frame start, render complete and display upload complete. Count complete new uploads separately from repeated scanout frames. Compare independent elapsed time to the guest's reported score. Check which time source SPMark actually uses. V5's general timer is 26 MHz and test-78's engine runs at 104/3 MHz; record programmed reloads, IRQ rates, time spent waiting, and observed guest seconds per system second before assigning any discrepancy to timers. Seek existing logs/results and run simulations immediately. Coordinate board access with Andrea before changing a running core.
3. Use the same original executable, inputs and ROM helpers in a full-board replay on **both production memory paths**, starting with the existing checked 36,608-pixel Sega replay and GLES frame fill, then a native SPMark 3D render/present interval. Mark Sega and GLES as proxies. Stock v5 already wins the extracted six-kernel comparison; the narrow kernels alone cannot establish the cause of the native deficit. Hold CPU geometry/TLB policy and memory service fixed in turn where possible. Record guest work (architectural instructions, user/kernel split, sampled PCs or helper-call counts), framebuffer/ordered-memory checksum and final visibility of posted stores.

### Bank-mapping check already run

An address-only calculation alternated byte address zero and each offset 512 times (1,024 requests, initially closed banks, one open row per bank, no refresh). V5 maps bank = address[23], row = address[22:10]. Donor maps bank = address[13:12], row = {address[24:14], address[11:10]}. At 4 KiB and 8 KiB spacing v5 predicts 1,023 conflicts and donor zero. At 16 KiB spacing both predict 1,023. At 8 MiB spacing the result reverses; at 32-byte spacing both predict zero. This is a mapping check, not an RTL latency or game measurement. Source anchors are v5 `rtl/ngage_sdram_adapter.v` and `rtl/sdram/jtframe_sdram64_bank.v`, donor `rtl/mem/sdram.sv`. Donor's earlier dirty-eviction loop also recorded a stride-sensitive cost (41.4 vs 32.1 clocks/load after changing D-cache capacity), which warrants testing the real traffic.
