# NEM-4 CPU strategy and comparison plan

## Decision on 17 November 2026

Keep improving the ARM920-compatible production CPU on `master`. Step 5E is running in the mainline Sol chat. The second candidate will be ngage2's **complete ARM9V2 CPU, caches and MMU**. First measure its historical larger cache on the current donor revision, then bring the whole subsystem up behind our board interface, improve it where the measurements justify a change, and compare the best qualified version of each CPU. The production selection remains open. Use the existing donor benchmark chat for the later donor work, one experiment at a time. ## Architectures and controls

| | Current NEM-4 implementation | Stock ngage2 donor | Planned larger donor |
|---|---|---|---|
| Execution | ZAP-based ARMv4T, registered load completion, overlapped resident stores, late store data, paired long-multiply delivery | Eight-stage ARM9V2, early operand/result bypass, branch/return prediction, sequenced block transfers | Same donor execution revision initially |
| Cache | 16 KiB I + 16 KiB D, 64 ways, 32-byte lines. Posted write-miss path helps streaming stores | 16 KiB I + 8 KiB D, two ways, 16-byte lines. Write allocation can fetch a whole line before overwrite | Target 32 KiB I + 32 KiB D, retaining donor ways, line size and policy for the first comparison |
| Translation and identity | ARM920-compatible CP15, separate 64-entry associative mixed-page TLBs, FCSE and lockdown | TI ARM925T identity, direct section buffers and page-size-specific buffers including two-way small-page TLBs | Keep donor translation constant for the capacity study. Audit NEM-4-visible behavior separately during integration |
| Reference | Accepted 5D `258eed3`; last routed version 5B `419471d` | Stock benchmark `23541bb`, QIP-selected `rtl/cpu/arm925t_gen.v` | Historical donor `6b30328:rtl/cpu/arm925t.sv` sets I to 32768 and passes 32768 for D. Use it as evidence for configuration, while retaining the newer execution and TLB code |

The earlier architecture review describes the proposed longer-term completion queue and AGU. The 5D schedule describes what production actually implements. Keep the NEM-4 cache geometry on the current-CPU track. Larger donor caches are an explicit alternative for evaluation. ## What prompted the next experiments

Cycle pairs below are medians at synthetic extra I:D waits `0:0` and `2:9`. The direct donor comparison froze our **5C**. The 5D matrix result is a separate same-work measurement.

| Fixed work | Our 5C | Stock ngage2 | Relevant observation |
|---|---:|---:|---|
| Matrix ×16 | 47,887 / 47,887 | 23,675 / 35,925 | 5D reached 45,736 at both profiles. On 5C, median call-to-helper and return-to-caller retirement gaps at 0:0 were 6 and 7 clocks, versus 1 and 1 on donor. Donor's 4 KiB-spaced buffers conflict in D-cache |
| Transpose ×32 | 3,591 / 3,591 | 1,910 / 3,484 | Our first load/store pair already retires faster. Donor recovers time on the following instructions and return. Its section descriptor walks account for most delayed-profile scalar reads |
| Original Thumb JPEG block | 84,353 / 84,353 | 36,251 / 36,631 | Large persistent gap on a call-heavy workload. Attribution requires a trace of actual target delivery and useful issue |
| Full-frame 16-bit fill | 71,259 / 201,302 | 105,069 / 275,892 | Our streaming path avoids scored external reads. Including the pending write drain at 2:9 gives 201,407 versus 275,892 |

Both small fill kernels favor the donor. Eight post-indexed stores retire one per clock on ngage2; on 5C the eighth retires 24 clocks after the first. This distinguishes a loop-carried base-update dependency from the 71-cycle plain 64-store test. The full report includes triangle, both tails, memory traffic, window definitions, negative controls and Thumb BL counting. ## Execution order

1. **5E, current CPU.** On exact 5D trace target known, fetch accepted, correct instruction available, first useful issue and retirement on repeated ARM matrix calls and Thumb JPEG calls/returns. Classify wrong-path drain, cache/TLB delay and backend holds. Implement one general improvement if the critical interval is recoverable. Preserve BL/LR, ARM/Thumb state, FCSE, precise faults and IRQ recovery under stalls and nested calls. Compare matrix, transpose, JPEG and the store stream against 5D. The next independent lead is post-indexed store base forwarding if 5E's traces or subsequent workload ranking support it.
2. **Restore donor capacity in the benchmark harness.** Pin stock `23541bb`. Generate the trial Verilog with the donor's source generation flow in an isolated build directory and verify the elaborated sizes and selected top. First change D from 8 to 32 KiB while holding I at 16 KiB, then grow I to 32 KiB with D fixed. Keep the original guest layout, cache policy, TLB and memory responder throughout. Check for hard-wired set/index widths. In particular, donor `zap_dcache.sv` passes an 8 KiB `INDEX_SIZE` to tag RAM for larger two-way configurations. Exercise index maintenance, aliasing, dirty eviction and conflicting addresses; prove increased usable capacity. Record CP15 cache-type readback separately from physical array geometry. Check matrix refills/writebacks, transpose descriptor reads, and frame allocation traffic to determine which losses capacity actually addresses.
3. **Integrate the whole donor CPU as an alternative.** Start from its measured subsystem and cross the existing `ngage_cpu` boundary. Elaborate one CPU per build. Adapt reset/vector, IRQ/FIQ, owned scalar requests/responses, byte enables, SWP lock, instruction/data classification, refill beats, errors and debug observation. Keep the same NEM-4 board, flash, SDRAM, MMIO, DMA arbitration, DSP, NOS and Bluetooth implementations. Preserve donor source revision, notices, generation recipe and local patches in the integration record. Compare the standalone and wrapped candidate on the same guests before interpreting a speed change. [Board-facing ports](../rtl/ngage_cpu.sv) · [CPU semantics and integration risks](cpu-donor-comparison.md)
4. **Qualify and improve the donor.** Exercise stock-firmware-visible CP15 ID/cache type, all page sizes, AP/domain faults, FCSE, lockdown, index/MVA maintenance, aliases, cacheable-fill errors, partial block transfers and interrupt return. Some differ between the stock donor and our ARM920 model. Record each observed mismatch and its remedy; changing an ID register alone cannot reproduce maintenance behavior. Then change one evidenced bottleneck at a time. Candidates include section-TLB conflicts and streaming write allocation if those costs survive resizing. Preserve the larger-cache pre-improvement result as its own control.
5. **Compare the two best candidates in the same phone design.** Freeze a revision for each. Run all six original ARM/GLES kernels and the separate original Thumb JPEG block at both profiles, with identical work, warmups, repeats and checked outputs. Report cycles per work unit, calls/returns, misses, walks, refill and writeback words and pending writes at the window boundary. Distinguish equal-clock throughput from achievable board frequency. Fit finalists under the same device, Quartus version, seed, debugger, PLL and constraints. Compare ALMs, occupied LABs, M10Ks, DSPs and per-corner timing at the actual 78 MHz and post-fit 104 MHz. Keep raw per-workload results visible alongside any summary. With later hardware authorization, compare boot and the same full SPMark workload on the same board configuration. Record the production choice and remaining compatibility or workload trade-offs.

## Evidence to retain at each step

For each tested revision, record the active architecture and exact inputs, hypothesis, before/after event schedule, fixed-work cycles, output and fault checks, measured traffic, fit or hardware evidence when available, and the decision to retain or reject. Mark proposed changes and unmeasured costs explicitly. Keep durable reports and replay helpers in the project and generated outputs under `build/`. At 5B only three LABs were free; use a matched fit to price the larger caches and board adapter. The actual PLL remains at 78 MHz.
