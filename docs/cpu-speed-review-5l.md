# CPU execution speed after 5L

Review of 17 November 2026. Keep the matched 5L and banked main-TLB fits as the physical decision. For the next simulation, test a third **D-side checked translation mapping** on the original pixel span. For the next instruction-pipeline experiment, test the existing early word-load path on ordinary Thumb loads. The two experiments address different stalls and should each have their own 5L control.

## A translation bottleneck inside a warm pixel loop

Each Super Monkey Ball pixel reads stack parameters, reads two source bytes and writes a destination halfword. The 512-pixel run has no external transfers in its scored window. Nevertheless, D-side translation repeatedly blocks the CPU. The main TLB holds 64 translations, but its two local checked mappings each cover only 1 KiB, even when the underlying descriptor maps a 1 MiB section. The fixture puts all three working regions in one such section. [Local mapping implementation](../rtl/arm920/tlb.sv) · [Fixture mappings](../tests/cpu/spmark_payload/workloads.py)

I replayed all 4,608 effective data addresses in each pattern from the saved 5L execute journal. The table counts misses in an initially empty FIFO of checked mappings. A hit leaves insertion order unchanged, as in the current design. This is an address-locality model with constant context. It does not simulate pipeline timing, actual initial TLB state or main-table replacement.

| Modeled local coverage | Forward misses | Reverse misses |
| --- | ---: | ---: |
| Two 1 KiB mappings | 1,537 | 1,537 |
| Three 1 KiB mappings | 10 | 10 |
| Two mappings capable of covering the fixture's actual 1 MiB section | 1 | 1 |

There is also direct timing evidence. In both patterns, the complete iterations between edges 153 and 1,380 cover 18 pixels in 1,227 clocks. Outstanding data demands see translation busy for 162 clocks. These split equally across the first source-byte read, destination store and subsequent stack load. On 144 of those clocks the global data hold is asserted. That is eight coincident hold clocks per pixel. Some cache or dependency work may still occupy those clocks after translation improves. The saved journal covers only the first 1,400 edges at this signal detail. [5L events](evidence/cpu-late-operand-20261117.events.json.gz) · [Observer definitions](../tests/cpu/cpu_late_operand/observe.vh)

The full issue journal independently shows two intervals worth following. From the second byte load to the pixel combine there are 10 or 15 clocks, totaling 5,600 forward and 5,525 reverse. From the stack load following the store to its dependent ADD there are 14 or 17 clocks, totaling 7,363 in each pattern. At one representative forward pixel the byte loads already acknowledge on consecutive edges 526 and 527. Earlier translation on the first demand can help a different part of the interval than an extra data port could. [Span and timing boundaries](super-monkey-ball-span.md)

**First experiment.** Give the D side one more 1 KiB slot under the existing shared context and FIFO publication policy. It can cover the three regions even when real software places them on separate pages. Compare both original patterns with 34,995 / 34,920 clocks. Repeat with the same work under separate small-page mappings and distinct physical bases. Check actual retirements, both bytes of every store, precise permission faults, context changes and revocation on main-table mutation. Keep the current fast translation and completion combinational paths visible in the routed comparison. This adds a comparator and a result choice on a path already under timing pressure.

Experiment 1 reproduced the span clocks and tested the same guest work with the stack, source and destination backed by distinct small pages. In the scored RTL windows, searches dropped from 1,536 to 9 and the original spans used 11.21–11.27% fewer clocks. [RTL qualification and workload scorecard](cpu-third-data-mapping.md)

An alternative is to record the descriptor kind and give a **section** mapping its actual reach, taking the low 20 PA bits from the current modified virtual address. This would avoid another slot, while adding range and physical-address selection. Keep page grants at their existing 1 KiB coverage in this version, and keep exact walk faults tied to their original address and direction. Test a nonidentity section and adjacent small-page subpages with opposite permissions. The one-section benchmark favors this design by construction. Descriptor kinds and locality from a representative game or firmware trace would decide how broadly it helps. [Permissions, physical address construction and lifetime](../rtl/arm920/tlb.sv)

The existing bank experiment reduces the cost in logic of the 64-entry table. These proposals reduce how often a warm request needs that table. Matrix and JPEG already have measured full-search activity on 5L, with 1,904 and 3,972 clocks respectively in the union of I/D lookup waits. Those totals include both sides and give no estimate of a D-only change's savings. [TLB area and performance study](tlb-area.md)

## The existing early-load path has a Thumb coverage gap

The Thumb decoder already translates ordinary immediate word loads and SP-relative word loads to the same internal load shape as their ARM equivalents. Predecode excludes Thumb from the eligible class, and the P1 early-start check also tests the instruction-state bit. This explains why a large set of real instructions never exercised the 5J/K/L combination. [Thumb decoder](../rtl/arm/zap_mode16_decoder.sv) · [Class selection](../rtl/arm/zap_predecode_main.sv) · [P1 start and load-pair rules](../rtl/arm/zap_core.sv)

In the original 8×8 JPEG converter, **3,864** of the 22,500 executed instructions are ordinary Thumb word loads with an immediate offset and **1,224** are SP-relative word loads. Of those 5,088, the immediately following instruction is a dependent ADDS **1,001** times and a dependent CMP **146** times. All 1,147 pairs also occur in the archived 5F scored retirement stream. Their issue intervals range from 7 to 24 clocks there. 5F and 5L both measure 84,353 median clocks on the block. One net clock on every one of the 1,147 pairs would be 1.36% of the block. Other load combinations may benefit from earlier lookup or issue. Eligibility, overlap with older work, and elapsed gains need a candidate run. [Original JPEG scorecard](cpu-integrated-5f.md) · [5L qualification](cpu-late-operand.md)

**Second experiment.** Classify only these two single-instruction Thumb load formats for the early registered lookup and P1 start. Include the flag-setting Thumb consumer in the checks. Keep the existing precise owner, alignment and fault rules. The class bit has other users, including adjacent-load and load-to-store paths. Keep ARM-specific adjacency assumptions isolated, especially four-byte PC spacing. Exercise both Thumb halfword positions, a faulting load followed by a flag writer, and an interrupt or ARM/Thumb transition at the boundary. Compare JPEG cycles, dependent execution and retirement, alongside the existing 224-in-224 ARM stream and game results. Decide on Thumb stores, PUSH/POP or additional ALU operations from separate measurements.

Experiment 2 reproduced the qualified ARM stream and shortened the four original JPEG cases by 2.83–3.03% and the full Sega Rally screen scan by 2.12–2.15%. The isolated Thumb overlay passed exact fault and state-switch checks. [Full measurement and decision](cpu-thumb-early-load.md)

## What changes the larger plan

5L gives about **1.343×** geometric six-kernel throughput over the original review at zero added memory waits. The separate JPEG block improved from 89,610 to 84,353 clocks. The last audited 5K fit used 40,834 / 41,910 ALMs and missed 78 MHz setup by 1.069 ns at the worst corner. The matched 5L fit reports were still uncollected in the local record. Compare routed setup and hold at 78 and 104 MHz as well as ALMs and M10Ks before selecting a physical baseline. [Fixed-work baselines](cpu-integrated-5f.md) · [5L six-kernel results](evidence/cpu-late-operand-six-20261117.json) · [5K timing](cpu-load-release.md) · [Matched fits](tlb-matched-fit.md)

The original 4× same-clock target exceeds the review's optimistic single-issue six-kernel bound of 3.91× even at zero added waits. The present span alone takes 34,995 clocks for 10,240 instructions, an ideal one-retirement-per-clock ceiling of about 3.42× from 5L. Revisit wider execution if a measured workload needs it after translation and instruction coverage improve. For gameplay, the separate Sega Rally capture places 227 of 357 fetch samples in firmware, including 44 at a cache-maintenance loop branch. A timed replay of the real maintenance loop with realistic clean and dirty line mixes would distinguish CPU issue time from writeback and drain latency. There is no whole-game FPS estimate from those samples. [Original ceilings and assumptions](cpu-pipeline-architecture-review.md) · [Sega Rally capture](sega-rally-profile.md)

### Reproducing the trace counts

For each pattern in the 5L events, select `LATE_EXEC.result` for memory-operation offsets 0x00, 0x10, 0x14, 0x20, 0x28, 0x2c, 0x34, 0x38 and 0x44 relative to 0x10093e38. The observer records the registered ALU address. Each pattern has exactly 512 occurrences per offset. Feed the addresses in their recorded order to the stated FIFO models. For the timing sample, filter `PIPE_EDGE` to `153 <= t < 1380` and count `offer && busy` and its intersection with `stall`.

For JPEG, weight the original Thumb halfwords by the per-PC counts in `build/sim/jpeg-payload/step5l-jpeg-01/oracle.json`, using the ROM hash verified by the [JPEG fixture](../tests/cpu/jpeg_profile/workload.py). Select halfwords whose upper five bits are 01101 or 10011. For the dependent subset, decode the fallthrough instruction and check that it reads the producer's destination register. The independent 5F `TARGET5E` journal in `build/sim/jpeg-payload/useful-target-5f-jpeg-01/` pairs these loads and their sequential successors in actual retirement order. The load and consumer dequeue edges precede their respective retirements.
