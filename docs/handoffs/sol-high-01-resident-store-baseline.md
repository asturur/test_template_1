## What to build

1. Start from `tests/cpu/cache_resident/test.v` and its `sim.sh`. Its existing `access` task waits for each response and drains the buffer before issuing again. Keep those latency and correctness tests. Add a streaming test mode or sibling fixture that uses the actual `arm920_cache_access`, bank, tags and RAMs. Keep the workload generator and expected-data model independent of the DUT. Put hierarchy-specific observations in one place so the next implementation can reuse the test.
2. Warm real lines through ordinary cache requests. Drive at least 256 ordinary cacheable write-back store offers per measured stream. Keep the next offer present whenever work remains, hold payload stable until accepted, and advance the generator only on acceptance. Do not insert a wait for ACK between offers. Cover (a) successive words and both dirty halves of one line, (b) alternating two resident lines, and (c) repeated partial-byte writes to the same word. Use deterministic, distinguishable payloads and nonzero masks. Include directed cases that dirty just the lower or just the upper half. Separate warm-up and final readback from measured clocks.
3. Sample on a stated rising-edge convention. Record offer, accepted request, sampled response and actual data-RAM mutation separately. For each accepted store, check exactly one ordered response and the matching RAM-write slot, word, bytes and value. Derive expected bytes from the accepted address/data/mask and independent initial memory. Verify dirty-half behavior through the actual tag/clean/writeback effects, and verify final bytes by ordinary reads or backing-memory readback after clean. Count external transfers during the measured resident-only burst. A queued request or early ACK alone cannot count as a committed store.
4. Report first-accept-to-first-commit latency, first/last accept and commit edges, accepted and committed counts, and interval histograms for successive accepts and successive commits. Give a short edge trace for two adjacent stores. For N events, steady-state rate is (N−1)/(last edge−first edge). The recorded CPU transpose witness accepted stores on 44/48 and committed on 47/51. Use it as a cross-check. A standalone cache driver has different boundaries; explain any difference from observed traffic or source. The current baseline passes on correct ownership/data and honest measurements. One store per clock is the **future candidate's** gate.
5. Run the existing resident-cache fixture and the new streams. Demonstrate that the new checker rejects at least one deliberate wrong result, such as an incorrect expected byte or a duplicated commit event supplied to the checker. Keep the negative control test-only. Reproduce the normal result in a second run. Reuse the existing six-kernel/JPEG evidence here; this step changes only the testbench.
