# Step 4A — Let real ARM instructions use the resident-store pipeline

Read AGENTS.md and docs/status.md first. Work in the existing integration checkout, in an isolated offline overlay based on the verified Stop 3C design. Keep the PLL at 78 MHz. Start immediately, regardless of Stop 3D timing or run status. The deliverable is a working CPU performance experiment. Use registered local control suitable for the eventual 104 MHz target. Defer Quartus runs to a later integrated milestone.

1. Run a short ARM program through the real CPU: warm the D-cache, then execute an unrolled sequence of independent aligned STR-immediate instructions to resident ordinary write-back RAM. Time the same instruction window through its final drained store. Trace distinct instructions and the CPU issue, adapter acceptance, physical cache writes and architectural completion edges. Identify where the next eligible instruction currently waits for its predecessor. Use Stop 3C as the comparison and retain identical instructions, memory delays and output checks.
2. Change the CPU/adapter boundary so a second eligible STR can start while its predecessor's cache write is still in flight. Follow the hold upstream into CPU issue if the adapter alone cannot produce overlap. Choose the smallest useful amount of registered ownership/credit. Start with unconditional, aligned, no-writeback stores with resolved operands, translation, permission, physical destination and a certified resident slot. Respect older faults and redirects before allowing an irrevocable effect. Preserve store order, byte masks and exactly-once replies. Use the existing serialized route for other operations. Avoid a fixed eight-entry implementation unless measurements justify it.
3. Show the first overlapping pair in an edge trace and report cycles per architectural store, total cycles through drain, and actual writes before/after. The favorable target is one architectural start per clock. If a correct prototype achieves an intermediate gain, quantify it and identify the next lost cycles. A direct-cache stimulus or earlier ACK alone cannot establish CPU progress. If the first attempt gives zero gain, use the trace to fix the next serial dependency in this run.
4. Verify final bytes and dirty writeback against an independent oracle. Target the risks introduced by multiple owners: held requests under backpressure, a following same-address load, transition to an ineligible access, and an older fault/interrupt boundary with no younger leaked store. Reuse existing tests for unchanged paths. Run one representative original store-heavy fixed-work kernel (e.g. transpose), compare output and cycles against 3C, and explain how often its stores qualify. Expand testing where a failure or a changed contract calls for it.

Deliver a replayable candidate and a short report with the two cycle comparisons, architectural correctness checks and the next limiting dependency. Keep the phone, production RTL and existing simulations untouched. Leave any in-flight fit alone; its result is context for subsequent design work.
