# Step 5H — find the first useful instruction after a taken transfer

Research only. Use the existing master checkout and the accepted 5F CPU at `8e70b1e`. Read `AGENTS.md`, `docs/status.md`, the [5F scorecard](../cpu-integrated-5f.md), the [5E call/return experiment](../cpu-target-delivery.md) and the [5G crossing trace](../cpu-store-crossing.md). The objective is to choose a frontend mechanism that can shorten elapsed cycles on original workloads. Use the existing offline simulator only if existing receipts lack an essential signal. The Quartus job can run independently.

1. Start with original ARM matrix at 0:0. Its helper call and return repeat 1,024 times. Use the existing 5E event journals or extend their passive observer on frozen 5F. For each dynamic transfer, identify the architecturally correct successor from checked execution, then measure the first clock the hardware could actually know that successor. Follow that occurrence through target selection, held request, permitted I-cache response, fetch FIFO, ARM/Thumb assembly, predecode, decode and **actual operand dequeue**. Verify the issued PC against the retired stream. Label stalls by the first stage preventing useful advance, including downstream holds and older wrong-path work. Count overlapping intervals once.
2. Repeat on original Thumb JPEG using a common direct call, a return correctly identified by the return stack, and a return corrected later. Use the byte-fill loop backedge as a short control. Compare phase and instruction type. The existing traces report five to six clocks from fetch acceptance to decode in representative classes. Determine which are occupied by useful older instructions, which can overlap, and which leave a real bubble. Treat a mature BTB prediction and a corrected return-stack target separately.
3. Model **one** registered change where the measured stall occurs. For example, if the correct instruction word is already present but waits to re-enter the frontend, test whether an existing registered queue slot can hold its address, context and word until normal decode can accept it. If the word arrives late, identify the actual translation, I-cache or held-demand owner before proposing storage. Use only information available at that clock. Keep held transactions stable and later corrections authoritative, qualify code with the original translation/permissions and ARM/Thumb state, honor I-cache maintenance and deliver a live prefetch fault exactly once. Speculative work must not create device reads or architectural effects. Budget the added bits, comparisons, RAM ports and registered edges at the 104 MHz design target with the physical PLL at 78 MHz.
4. Deliver one event schedule before and after the modeled change and a per-workload count of plausibly exposed saved clocks. Show measured facts and counterfactual estimates separately. As a proposed screen for funding an RTL prototype, look for roughly 5% on matrix (2,287 clocks) or JPEG (4,218 clocks), with evidence that the same mechanism helps another workload. These are planning targets. Do not sum every empty queue clock or assume a one-cycle-earlier request automatically advances useful issue. If the bound is small, identify the structural change the evidence supports and end the step.

Write a short report and machine-readable receipts. Leave production RTL, the donor checkout and the running phone alone. No new fit or payload is needed for this decision.
